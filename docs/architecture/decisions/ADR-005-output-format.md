# ADR-005: Output Format - Markdown + JSON

## Status

Accepted

## Context

AgentScope generates documentation and data files that users will:

1. **Read in GitHub/GitLab** - View rendered documentation in repository
2. **Review in PRs** - See changes when agent configs are updated
3. **Process programmatically** - Integrate with other tools and CI/CD
4. **Share with teammates** - Send links to documentation

The output must be:
- **Human-readable** - Clear structure, embedded diagrams
- **Machine-readable** - Structured data for tooling integration
- **Diff-friendly** - Changes visible in version control
- **Self-contained** - No external dependencies for viewing

The PRD specifies the following output structure:
```
docs/agent-architecture/
├── README.md          # Overview with diagrams + TOC
├── AGENTS.md          # Detailed agent docs with code examples
└── raw/
    └── agentscope.json  # Raw unified config (for tooling)
```

## Decision

We will output **Markdown files with embedded Mermaid diagrams** for human documentation, and **JSON files** for machine-readable data.

### Output Structure

```
docs/agent-architecture/
├── README.md              # Entry point: overview, stats, diagrams
├── AGENTS.md              # Detailed per-agent documentation
└── raw/
    └── agentscope.json    # Complete unified config as JSON
```

### Formatting Rules

1. **Markdown**:
   - Use ATX-style headers (`#`, `##`, `###`)
   - Tables for structured data
   - Code blocks with language hints
   - Mermaid diagrams in fenced blocks

2. **JSON**:
   - 2-space indentation
   - Sorted keys for consistent diffs
   - ISO 8601 dates
   - No trailing commas

3. **File Encoding**:
   - UTF-8 for all files
   - LF line endings (Unix-style)

## Consequences

### Positive

- **Universal readability**: Markdown renders everywhere (GitHub, GitLab, VS Code, etc.)
- **Native diagram support**: Mermaid renders without external tools
- **Tooling integration**: JSON enables CI/CD and programmatic access
- **Clean diffs**: Text formats show meaningful changes in PRs
- **Self-documenting**: README.md serves as entry point for new team members

### Negative

- **Regeneration required**: Changes to agents require re-running AgentScope
- **Stale risk**: Documentation can drift from actual config if not automated
- **Multiple files**: Three files to maintain (mitigated by generation)

### Neutral

- Markdown styling is limited (no custom CSS)
- JSON file can grow large for complex configurations

## Options Considered

### Option 1: Markdown Only

Generate only Markdown files, no JSON.

- **Pros**: Simpler output, single format
- **Cons**: No machine-readable option, harder to integrate with tools
- **Why rejected**: Tooling integration is important for CI/CD

### Option 2: JSON Only

Generate only JSON, let users render it.

- **Pros**: Maximum flexibility, single source of truth
- **Cons**: Requires additional tooling to view, not human-friendly
- **Why rejected**: Contradicts "understand in 30 seconds" goal

### Option 3: Markdown + JSON (Chosen)

Generate both human-readable and machine-readable formats.

- **Pros**: Best of both worlds, serves different use cases
- **Cons**: Multiple output files
- **Why chosen**: Matches PRD requirements, serves all user needs

### Option 4: HTML Static Site

Generate a static HTML documentation site.

- **Pros**: Rich formatting, interactive features possible
- **Cons**: Overkill for v1.0, requires hosting or local server
- **Why rejected**: Deferred to v2.0 if demand exists

### Option 5: Single README.md

Everything in one file.

- **Pros**: Simplest possible output
- **Cons**: Large file, no separation of concerns, harder to navigate
- **Why rejected**: Doesn't scale for complex configurations
